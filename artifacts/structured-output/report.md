# Отчет по заданию №1
## Получение ответа от LLM в определенном формате

**Проект:** Цифровой сотрудник для анализа качества RAG-системы
**Репозиторий:** `rag-quality-agent`  
**Рабочая ветка:** `task/01-structured-output`  
**Дата:** 27.11.2026

## 1. Цель работы

Реализовать прототип HTTP API на Python и FastAPI, который обращается к LLM через OpenAI-совместимый интерфейс, передает заданную температуру генерации и возвращает JSON, соответствующий заранее определенной схеме.

Для связи со сквозным проектом выбран сценарий оценки одного ответа RAG-системы.

## 2. Постановка задачи

Приложение должно принимать вопрос, оцениваемый ответ, эталонные и найденные чанки, после чего возвращать бинарную оценку, теги ошибок и краткое обоснование.

По результатам обсуждения с куратором уточнила входной контракт:

- поле `reference_answer` исключено, поскольку эталонный ответ может отсутствовать;
- добавлено поле `reference_context` с текстами эталонных чанков из разметки;
- для обоих наборов чанков используется тип `list[str]`, без идентификаторов;
- формирование входных данных оставлено за рамками задания;
- выбор модели разрешено сделать исходя из доступности;
- для получения структурированного результата рекомендовано сэмплирование с ограничениями.

В прототип не входят расчет метрик Retrieval, адаптер данных, обработка файлов и формирование Excel-отчетов.

## 4. Подход реализации

Приложение разделено на несколько модулей:

| модуль | назначение |
|---|---|
| `app/schemas.py` | Контракт запроса, результата и правила валидации |
| `app/config.py` | Загрузка и проверка конфигурации |
| `app/llm.py` | Формирование запроса к LLM и проверка ее ответа |
| `app/main.py` | HTTP endpoint и обработка ошибок |
| `app/check_llm.py` | Демонстрационный вызов реальной модели |
| `app/experiment.py` | Повторные запросы при разных температурах |

Обработка запроса выполняется в следующем порядке:

1. FastAPI получает тело HTTP-запроса.
2. Pydantic проверяет входные данные.
3. Приложение формирует сообщения для LLM.
4. В OpenAI-совместимый API передаются модель, температура и JSON Schema.
5. Проверяется завершение генерации и наличие содержимого.
6. JSON проверяется через модель `EvaluationResult`.
7. Клиент получает результат либо описание ошибки.

Клиент LLM создается при запуске FastAPI-приложения и закрывается при его остановке через механизм `lifespan`.

### 4.1. Входной контракт

Реализован endpoint `POST /evaluate`.

| поле | тип | правила |
|---|---|---|
| `question` | `str` | Обязательный непустой вопрос; пробелы по краям удаляются |
| `answer` | `str` | Обязательное поле; пустая строка допускается |
| `reference_context` | `list[str]` | Обязательный список эталонных чанков; может быть пустым |
| `context` | `list[str]` | Обязательный список найденных чанков; может быть пустым |
| `temperature` | `float` | Необязательное конечное число от 0 до 2 |

Диапазон температуры 0–2.

Если температура явно передана в запросе, используется ее значение. Иначе используется настройка `LLM_TEMPERATURE`.

Неизвестные поля запрещены.

### 4.2. Выходной контракт

| поле | тип | назначение |
|---|---|---|
| `score` | `int` | Бинарная оценка: `0` или `1` |
| `tags` | `list[str]` | Теги обнаруженных ошибок |
| `explanation` | `str` | Непустое обоснование оценки |

Реализованы дополнительные правила:

- при `score = 1` список тегов должен быть пустым;
- при `score = 0` требуется хотя бы один тег;
- теги не должны повторяться;
- разрешены только значения из справочника;
- для `score` запрещено неявное преобразование строк, логических значений и чисел с плавающей точкой.

Справочник содержит теги `wrong_chunks`, `not_full`, `hallucination`, `fact_distortion` и `verbose`.

Тег `retrieval_error` не выставляется, поскольку оценка Retrieval в текущем задании не реализуется.

### 4.3. Структурированный вывод

JSON Schema формируется методом `EvaluationResult.model_json_schema()` и передается в параметре `response_format` с типом `json_schema`.

Таким образом, схема передается серверу генерации, а не только описывается в тексте промпта.

После получения ответа вызывается `EvaluationResult.model_validate_json()`. Эта проверка дополнительно контролирует правила, реализованные Python-валидаторами: уникальность тегов, непустое обоснование и согласованность полей.

Лимит генерации составляет 512 выходных токенов. Автоматические повторные запросы SDK отключены, чтобы каждая попытка эксперимента учитывалась отдельно.

### 4.4. Промпт оценки

Промпт задает критерии точности, полноты, соответствия вопросу и опоры на найденный контекст.

В нем различаются:

- `answer` - непосредственно оцениваемый ответ;
- `reference_context` - эталонные материалы для проверки;
- `context` - материалы, доступные исходному генератору.

Входные тексты рассматриваются как данные для анализа, а не как инструкции оценщику. Использование внешних знаний запрещено.

Промпт является стартовым вариантом. Его содержательная эффективность проверялась на небольшом синтетическом наборе и требует дальнейшего исследования.

## 7. Эксперимент с температурой

### 7.1. Методика

Использован один вопрос:

> Во сколько открывается и закрывается тестовый сервис?

Эталонный и найденный контексты совпадали:

> Тестовый сервис работает ежедневно с 09:00 до 18:00

Подготовлены три варианта ответа:

| пример | ответ | ожидаемый `score` |
|---|---|---:|
| `correct` | Тестовый сервис открывается в 09:00 и закрывается в 18:00 | 1 |
| `distortion` | Тестовый сервис открывается в 10:00 и закрывается в 18:00 | 0 |
| `incomplete` | Тестовый сервис открывается в 09:00 | 0 |

Для каждого примера выполнены два запроса при температурах `0.0`, `0.5` и `1.0`.

Всего: 3 примера * 3 температуры * 2 повтора = 18 попыток.

Запросы выполнялись последовательно, в фиксированном порядке. Ошибки не исключались из учета.

Для каждой попытки сохранены:

- вариант ответа и ожидаемая оценка;
- температура и номер повтора;
- статус проверки;
- результат либо тип ошибки;
- время выполнения.

Время измерялось вокруг вызова функции оценки и включает обращение к серверу и проверку результата.

Результаты сохранены в файле:

### 7.3. Анализ содержательных ошибок

| пример | совпадения бинарной оценки | наблюдение |
|---|---:|---|
| `correct` | 6/6 | Правильный ответ во всех попытках признан корректным |
| `distortion` | 5/6 | Искажение обычно обнаружено, но выбран тег `not_full` |
| `incomplete` | 0/6 | Пропуск времени закрытия не обнаружен |

В примере `distortion` время открытия заменено с 09:00 на 10:00. В пяти попытках модель выставила оценку `0`, однако выбрала `not_full`. По принятому описанию тегов данная проблема соответствует искажению факта.

При температуре `0.5` один из двух повторов для этого примера дал ошибочную оценку `1`. Следовательно, на данном примере наблюдалась нестабильность бинарной оценки.

В примере `incomplete` во всех шести попытках выставлена оценка `1`, хотя ответ не содержит времени закрытия. Некоторые обоснования утверждают, что это время присутствует в ответе, хотя оно содержится только в контексте.

Наблюдения позволяют предположить смешение моделью содержания оцениваемого ответа и источников. Для установления причины необходимы дополнительные проверки.

### 7.4. Интерпретация времени выполнения

Первый запрос занял 12 секунд, остальные - от 2 до 7 секунд.

По этой серии нельзя заключить, что увеличение температуры ускоряет генерацию. Порядок запросов фиксирован, состояние модели в памяти и влияние загрузки отдельно не контролировались. Длина сгенерированных обоснований также различалась.

## 8. Ограничения

1. Эксперимент содержит только три уникальных синтетических примера с повторами. Результат 11/18 характеризует эту серию, а не общее качество оценщика.
2. Независимая экспертная разметка отсутствует.
3. Совпадение бинарной оценки не гарантирует правильность тегов и обоснования.
4. Валидность JSON и согласованность полей не подтверждают содержательную корректность результата.
5. Обработка длинных входов и контроль переполнения контекста отдельно не реализованы.
6. Надежность защиты промпта от инструкций во входных материалах отдельно не исследовалась.
7. Работа с другими моделями и провайдерами требует проверки совместимости.
8. Стоимость локальных вычислений, энергопотребление и сокращение времени ручной проверки не измерялись.

## 9. Выводы

Реализован прототип API на Python и FastAPI, который обращается к локальной LLM через OpenAI-совместимый API, передает температуру и получает структурированный результат по JSON Schema.

Подготовлены конфигурация, модели данных, обработка ожидаемых ошибок, демонстрационный сценарий, автоматические тесты и эксперимент.

Все 27 автоматических проверок прошли. В реальной серии все 18 результатов прошли проверку схемы и реализованных правил, однако бинарная оценка совпала с ожидаемой только в 11 попытках.

Таким образом, технический механизм получения структурированных ответов продемонстрирован. Содержательное качество оценщика требует дальнейшей работы: уточнения критериев и промпта, сравнения моделей и проверки на независимой размеченной выборке.
